# Ad Studio

אפליקציה ליצירת מודעות בתהליך של משרד פרסום. הצד השרתי ב-Node.js (Express), הצד הקדמי ב-Vue 3, מסד הנתונים SQLite, והיצירה נעשית ב-Gemini עם המפתח של כל משתמש.

## השלבים

| # | שלב | מה קורה בו |
|---|------|------------|
| 1 | העסק וניתוח | טופס בריף. Gemini מנתח את העסק ואת המטרה. עדיין לא נוצרת תמונה. |
| 2 | פרטי חובה | הטקסטים שיופיעו במודעה, בדיוק כפי שנכתבו. |
| 3 | עשרה קונספטים | לכל קונספט: מה רואים, הרעיון, המסר, ולמה עוצרים. |
| 4 | קומפוזיציה | הקונספט הנבחר מפורק לתוכנית מלאה ולאלמנטים נפרדים עם מיקום. |
| 5 | ביקורת | בדיקה של גנריות, מסר, מוקד, עומס ומשיכת עין. אחריה בוחרים בין התוכנית המשופרת למקורית. |
| 6 | אלמנטים | כל אלמנט נוצר לבד: רקע, שולחן, כוס וכו'. אפשר לתקן אותו, להעלות צילום אמיתי במקומו, ולאשר גרסה אחת. |
| 7 | הרכבה ואיחוד | גרירה על קנבס עם הסרת רקע כרומה, ואז Gemini מאחד הכול לצילום אחד. בוחרים ומאשרים בסיס. |
| 8 | טקסט וייצוא | הטקסטים מעל הבסיס בפונטים של המשתמש, העלאת לוגו, וייצוא PNG ברזולוציה מלאה. |

בנוסף לשלבים:

- **ארגונים והזמנות במייל**: משתמש יכול להיות בכמה ארגונים, וההזמנה אישית לכתובת.
- **שחזור סיסמה במייל**.
- **ספרייה לכל ארגון**: פונטים ואלמנטים. כל אלמנט שמאושר נשמר בה, וכל פריט אפשר לסמן "כולם" כדי שיהיה זמין לכל הארגונים.
- **מכסות חודשיות** לארגון.
- **rate limiting** להתחברות, לשחזור סיסמה, להזמנות וליצירה.

את ההחלטות וההתלבטויות לאורך הבנייה אפשר למצוא ב-[DECISIONS.md](DECISIONS.md).

## דרישות

- Node.js 20 ומעלה (נבדק על 22)
- כדי להריץ את E2E: Python 3 עם Playwright ו-Chromium

## הרצה מקומית

```bash
npm run install:all
npm run build                         # בונה את web/dist, והשרת מגיש אותו
APP_SECRET=$(openssl rand -hex 32) npm start
# http://localhost:3000
```

אפשר להריץ בלי מפתח ובלי עלות, במצב הדגמה:

```bash
GEMINI_MOCK=1 npm start
```

לפיתוח עם hot reload:

```bash
npm run dev:server        # port 3000
npm run dev:web           # port 5173, proxy ל-/api
```

אחרי ההרשמה נכנסים להגדרות ומדביקים את מפתח ה-Gemini מ-Google AI Studio. המפתח מאומת ונשמר מוצפן.

## משתני סביבה

המשתנים מפורטים ב-`.env.example`. שני המשתנים שחייבים להגדיר ב-production:

- `APP_SECRET`: חובה. הוא מצפין את מפתחות המשתמשים, ושינוי שלו מאלץ את כולם להזין את המפתח מחדש.
- `APP_URL`: חובה. כל הקישורים במיילים נבנים ממנו.
- `SMTP_URL` ו-`MAIL_FROM`: חובה. בלי מייל אין איפוס סיסמה ואין הזמנות, ולכן השרת לא יעלה בלעדיהם.
- `TRUST_PROXY=1`: רק כשהשרת רץ מאחורי proxy. בלי proxy אסור להגדיר את זה, כי כך אפשר לזייף IP ולעקוף את הגבלות הקצב.
- `PLATFORM_ADMINS`: אימיילים של מי שמורשה לשנות מכסות.
- `DATA_DIR`: התיקייה שמכילה את ה-DB ואת כל הקבצים. זו התיקייה שמגבים.

## פריסה (Windows Server או Linux)

1. `npm run install:all && npm run build`
2. מגדירים `NODE_ENV=production`, `APP_SECRET` ו-`DATA_DIR`, ומריצים את `npm start` תחת מנהל תהליכים (pm2, NSSM או systemd).
3. מציבים מאחורי HTTPS: IIS ARR, nginx או Cloudflare Tunnel. ה-cookie מוגדר `Secure` ב-production, ולכן בלי HTTPS לא תהיה התחברות.
4. **גיבוי**: לפני כל שדרוג מגבים את `DATA_DIR` כולו (`adstudio.db`, קובצי `-wal` ו-`-shm`, ותיקיית `files/`). הכי בטוח לעצור את השרת לפני כן.

**Migrations**: הן רצות אוטומטית בעלייה, append-only, לפי `PRAGMA user_version`. מעבר לגרסה 2 **בונה מחדש את טבלת `fonts`**, ולכן חובה לגבות לפני כן (פירוט ב-DECISIONS D33).

**Rollback**: עוצרים את השרת, מחזירים את `DATA_DIR` מהגיבוי ואת הקוד לגרסה הקודמת, ומפעילים. migration שכבר רצה לא מתבטלת אוטומטית, ולכן חוזרים לגיבוי ולא "אחורה".

## מגבלות ידועות

- הקריאות ל-Gemini האמיתי לא נבדקו מסביבת הבנייה, כי הגישה ל-Google חסומה שם. שמות המודלים ניתנים להגדרה ב-`GEMINI_TEXT_MODEL` וב-`GEMINI_IMAGE_MODEL`.
- הגבלות הקצב נשמרות בזיכרון של תהליך יחיד. כשיש כמה instances צריך Redis או Cloudflare (D29).
- אין אימות אימייל בהרשמה (D31).
- שימוש בשם מסחרי, לוגו או אריזה של מותג אמיתי דורש הרשאה מבעל המותג.
